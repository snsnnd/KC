# 生产安全审计报告

## 范围与结论

本报告记录已确认的生产事实和当前仓库中的修复状态，不包含真实密码、Token 或个人信息。本轮整体审计与修复范围实际同时覆盖后端代码、前端、部署配置、自动化测试和文档；各项状态按“仓库是否修复”和“是否已经部署验证”分别记录。

审计开始时，生产 API 与当时本地源码哈希一致；随后仓库已继续修复并新增协作功能，因此完整发布前后必须重新核对哈希。生产现有 JSON 文件均可解析，`npm audit` 报告 0 个已知依赖漏洞，Nginx 已配置基础安全响应头。这些正向结果不能抵消主机入口、备份和业务授权层面的风险。

状态含义："已准备"表示仓库中已有配置或文档修复，但尚未证明已部署；"待处理"表示仍需授权运维或开发工作。

## 严重

### 1. Root SSH 密码已暴露且允许密码登录

- 证据：本次沟通中曾暴露生产 root 密码；生产 SSH 开启 root 密码认证，`PermitRootLogin yes`。
- 影响：持有该密码的人可能直接取得整台主机控制权，进而读取业务数据、环境密钥、邮件凭据和用户资料。
- 状态/计划：待立即处理。用户应立刻在可信终端轮换本次聊天中暴露的 root 密码，部署并验证密钥登录，再按变更流程禁用 root 密码登录。由于没有主机变更授权，本次审计不能也不会自行修改 SSH 配置，避免导致远程锁定。

## 高

### 2. 没有业务备份和恢复演练

- 证据：审计时不存在 `/var/lib/tech-club` 与环境密钥的业务备份。
- 影响：磁盘损坏、误删、JSON 写入中断或主机入侵都可能造成不可恢复的数据丢失；只有数据而没有同版本 `SESSION_SECRET` 时，加密配置也无法恢复。
- 状态/计划：已准备 `backup-tech-club.sh`、systemd service/timer 和恢复演练文档，待授权安装、首次手动备份、异地加密复制和实际恢复演练。本地备份与数据/密钥同机，不构成完整灾备。

### 3. 文件创建权限曾导致持续重启

- 证据：生产曾因无法创建 `bug-reports.json` 持续重启约 6886 次，临时创建空文件后恢复。
- 影响：单个新增持久化文件即可使 API 长时间不可用；快速重启还会增加日志、告警和运维负担。
- 状态/计划：临时故障已恢复。仓库 unit 已加入 `StateDirectory=tech-club`、`StateDirectoryMode=0750` 和 `UMask=0077`，确保服务可创建新文件，待上线验证。还应为启动时所需文件增加发布前清单和可写性检查。

### 4. JSON 跨文件审批不是事务

- 证据：库存、流水、使用申请和邮件 Token 分别写入不同 JSON；当前只有单进程串行锁和单文件原子替换，没有跨文件提交或回滚。
- 影响：进程退出、磁盘写满或 I/O 失败可能留下“已扣库存但申请仍待处理”等不一致状态，项目配额汇总也可能与审批记录偏离。
- 状态/计划：备份脚本在 SIGTERM 优雅停机成功后复制停止写入的文件，但这不是业务事务快照，也不能修复此前或运行时产生的跨文件不一致。短期应增加一致性巡检和人工对账；中期迁移到支持事务的数据库，在一个事务内更新审批、流水、配额和 Token。

## 中

### 5. 主机网络边界未收敛

- 证据：UFW 为 inactive。
- 影响：实际暴露端口完全依赖云安全组和各进程监听地址，错误监听可能直接暴露管理或内部服务。
- 状态/计划：待授权盘点监听端口、云防火墙和运维来源地址后，仅开放必要的 SSH、HTTP 和 HTTPS。不能在未确认远程访问路径时直接启用 UFW。

### 6. 审批职责分离（仓库已修复）

- 证据：原实现只校验管理员角色、面板和部门范围；当前仓库已在最终审批提交中比较管理员 `memberId` 与申请成员 ID。
- 影响：同时具有成员和审批权限的用户可能审批自己的材料或资金申请，形成利益冲突。
- 状态/计划：仓库已修复。后台与邮件审批的最终提交都会根据管理员关联的 `memberId` 拒绝自审，并已有回归测试；待部署验证。历史未关联 `memberId` 的管理员仍应逐步迁移到统一成员身份。

### 7. 停用成员审批复核（仓库已修复）

- 证据：原实现未在最终批准时复核成员；当前仓库已重新读取成员状态及 `material.request`/`fund.request` 权限。
- 影响：成员停用或离开后，历史待审批申请仍可能扣减库存或资金。
- 状态/计划：仓库已在审批确认时重新校验成员状态和对应申请权限，停用或失权后不能批准，并已有回归测试；待部署验证。自动撤销申请与 Token 仍应在迁移事务数据库后实现。

### 8. 项目配额服务端强约束（仓库已修复）

- 证据：仓库已实现 `project-workspaces.json`、对象级成员/负责人权限、任务、动态和资源配额；`used` 与 `pending` 从关联使用申请实时汇总，客户端不能直接写入。
- 影响：若只由客户端计算或人工填写 `used`，可能被绕过、重复累计，或在审批跨文件失败后失真。
- 状态/计划：仓库已修复并包含项目工作区端到端测试，待部署验证。审批、流水和工作区仍是跨 JSON 写入，因此事务风险没有解决，最终仍需迁移事务数据库。

### 9. 限流只保存在进程内存

- 证据：登录、申请、通知、审批和问题反馈使用进程内 Map 计数；重启会清空，且只对单实例有效。客户端 IP 依赖 `TRUST_PROXY_HOPS` 正确配置。
- 影响：攻击者可利用服务重启绕过窗口；未来多实例会分别计数；错误信任代理可能导致限流按伪造地址执行。
- 状态/计划：模板已把当前单层本机 Nginx 明确设为 `TRUST_PROXY_HOPS=1`。中期将认证和高价值接口限流迁移到共享、可持久化存储，并对代理拓扑变化做上线检查。

### 10. Nginx 上传 location 优先级和请求体范围过宽

- 证据：原配置全站 `client_max_body_size 110m`，`/api/` 与 `/uploads/` 没有 `^~`，静态扩展名正则可能改变 location 选择。
- 影响：非上传 API 接受不必要的大请求体，上传或媒体路径的处理规则可能被后续正则配置意外覆盖。
- 状态/计划：已准备配置修复。默认限制 2MB，仅精确 `/api/admin/upload` 放宽到 101MB；`proxy_pass` 不带 URI，保持原始上传 URI；`/api/` 和 `/uploads/` 改为 `^~`。待执行 `nginx -t` 并上线验证。

### 11. 运行身份共享且数据文件权限偏宽

- 证据：Nginx 与 Node.js 均使用 `www-data`；当前生产数据文件为 `0660`。
- 影响：Web 服务任一同身份进程被利用后，更容易读取或修改全部业务数据；组写权限扩大了修改面。
- 状态/计划：unit 已通过 `UMask=0077` 约束新文件并保持 `www-data` 以避免要求提前建用户。历史文件需在备份后单独收紧。后续迁移到专用 API 用户，并只向 Nginx 提供上传目录的最小读取权限。

### 12. 运行组件与证书部署需要生命周期管理

- 证据：生产运行 Node.js 24、Nginx 1.18；证书绑定 IP。
- 影响：旧 Nginx 的功能与安全维护窗口有限；IP 证书使 SNI、默认站点和迁移设计更易出错。
- 状态/计划：待确认操作系统供应商的安全补丁状态并规划滚动升级。Nginx 模板增加独立未知 Host 默认 server，只返回空连接，不暴露业务；仍复用现有证书路径，没有加入拒绝握手等可能破坏 IP 证书模板的激进配置。

## 低与正向控制

### 13. 安全响应头和静态缓存

- 证据：已有 HSTS、`X-Content-Type-Options`、`X-Frame-Options`、Referrer Policy、Permissions Policy 和 CSP。
- 影响：基础浏览器防护已存在；原 CSP 缺少显式 `object-src`，固定文件名 CSS/JavaScript 长缓存会延迟修复发布。
- 状态/计划：CSP 已准备加入 `object-src 'none'`；CSS/JavaScript 改为 5 分钟缓存，图片和视频为 30 天。待上线验证响应头。

### 14. 完整性与依赖检查结果

- 证据：生产 API 与本地源码哈希一致；所有审计 JSON 均可解析；`npm audit` 为 0 个已知漏洞。
- 影响：未发现发布文件漂移、现存 JSON 语法损坏或已知 npm 依赖漏洞。
- 状态/计划：持续在每次发布前后重复检查。哈希一致和 0 个已知漏洞不等同于业务逻辑安全，仍需完成上述授权与事务测试。

### 15. 上传内容校验（仓库已修复）

- 证据：原实现只检查客户端声明的 MIME。当前仓库会读取文件签名核对 JPEG、PNG、WebP、AVIF、MP4 与 WebM，类型不一致时删除文件并拒绝，同时按管理员限制上传频率。
- 影响：伪造类型和无限高频上传可能造成恶意文件托管或磁盘压力；文件签名检查仍不等同于完整解码、病毒扫描或磁盘配额。
- 状态/计划：基础校验已准备并有伪造 MIME 回归测试，待部署验证。后续应增加容量告警、总配额，并对高风险媒体执行解码转码或隔离扫描。

## 建议顺序

1. 立即轮换已暴露的 root 密码，验证密钥登录后按授权流程关闭 root 密码登录。
2. 安装并手动验证备份，建立加密异地副本，完成隔离恢复演练。
3. 在维护窗口上线 systemd 和 Nginx 修复，验证文件创建、未知 Host、上传上限、响应头和缓存。
4. 盘点主机端口并收敛防火墙规则，规划专用服务用户和 Nginx 升级。
5. 将进程内限流迁移到共享持久化存储，并最终迁移事务数据库。
