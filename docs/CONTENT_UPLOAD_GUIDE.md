# 项目与媒体上传规范

## 原则

- 只填写真实、可公开核验的项目和竞赛信息，不虚构名次、合作方、性能数字或成员贡献。
- 项目编号上线后保持稳定。建议使用 `SYS_001`，成果编号使用 `ACH_001`。
- 项目简介说明“解决的问题、核心方案、真实结果”，建议 40–160 字。
- 同一技术标签保持同一写法，每个项目建议 3–6 个标签，系统最多保留 10 个。

## 媒体

| 用途 | 推荐格式 | 推荐规格 | 命名示例 |
|---|---|---|---|
| 项目海报 | WebP / AVIF | 1600×1000 或更高，横向 16:10 | `SYS_004-poster-v1.webp` |
| 项目演示 | MP4 / WebM | 1080p，30–90 秒，无黑边 | `SYS_004-demo-v1.mp4` |
| 制作过程 | WebP / AVIF | 保留真实现场，不使用无关图库图 | `SYS_004-process-v1.webp` |

浏览器管理端支持一次选择最多 20 个媒体文件。上传前会统一检查类型、100MB 上限、图片或视频元数据；硬错误会阻止整批上传，命名、尺寸和压缩建议只作为提示。

## 批量项目

复制 `backend/config/project-upload.batch.example.json` 并填写项目。媒体路径相对于清单文件解析。先执行只读检查：

```bash
cd backend
BASE_URL=https://www.jtkczx.xyz \
ADMIN_USERNAME=your-account \
ADMIN_PASSWORD='your-password' \
npm run upload:project -- /path/to/projects.json --dry-run
```

检查通过后移除 `--dry-run`。工具会先校验整批清单和本地媒体，上传媒体后重新读取最新内容，并通过一次内容写入同时新增全部项目，避免逐项目保存覆盖其他管理员的修改。

媒体上传和内容保存是两个 API，不能形成数据库事务。如果媒体已经上传、后续文件或内容保存失败，工具会在原清单旁生成权限为 `0600` 的 `*.recovery-时间戳.json`。该清单把已上传媒体替换为服务器 URL、保留尚未上传的本地路径，可在排除失败原因后直接继续执行，避免重复上传已成功文件。

## 上线前检查

1. 海报与视频能正常打开，移动端海报主体没有被裁掉。
2. 项目编号、成果编号没有重复，成果关联到正确项目。
3. 外部链接使用 HTTPS，公开仓库和文档权限正确。
4. 项目名称、分类和技术标签写法一致。
5. 竞赛名称、名次、日期和图片已由资料负责人核对。
